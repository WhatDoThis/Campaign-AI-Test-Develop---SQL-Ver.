# Match C1~C6 · HUMAN 검증 가이드 (#154 DoD)

> **목적**: #154 값 인식 매칭이 서울≠인천 오탐을 실제로 막는지 콘솔에서 확인.  
> **누가**: 운영자(HUMAN). AI가 PASS로 처리하지 않음.  
> **선행**: #154 코드 배포 완료 · litmus `v=155` · JS lib `testWooMatch` / `testWooRepository` 재등록  
> **관련**: `22_매칭오탐_사고기록.md` · Option `testWooAiMatchEnabled`

## 0. 한 줄로 뭐 하는 건가

| 기호 | 의미 |
|---|---|
| **C1~C6** | #154 **완료 조건(DoD)** 6개 시나리오. **전부 통과**해야 Option을 켜 두고 운영 재개 |
| **SAME** | 같은 fragment **이름 + 값**이 질의·후보에서 같음 |
| **CONFLICT** | 같은 이름인데 **값이 다름** (예: 서울 vs 인천) → **목록에서 제외**되어야 함 |
| **MISSING** | 질의에만 있고 후보에는 없음 → 목록에 **남을 수 있음**(대조표에 “없음” 표시) |
| **동일** | 정규화 SQL 해시(`sqlContentHash`)까지 같음 → UI **「동일」** 배지 |

지금 Option이 **OFF**면 목록이 안 나옵니다. 아래 §1대로 **검증용으로만 잠시 ON** 하세요.

## 1. 검증 전 준비 (5분)

### 1-1. 배포 litmus
1. Studio URL 열기 → 진단/부팅 문구에 **`v=155`**, **`match=0` 또는 `match=1`** 확인  
2. `v=` 없으면 **캐시된 옛 클라이언트** → JSSP 재배포·강력 새로고침

### 1-2. Option 잠시 ON (검증용)
1. 콘솔 **Administration → Platform → Options**  
2. Option name: `testWooAiMatchEnabled`  
3. 값: **`1`** 또는 **`true`** (저장)  
4. Studio 새로고침 → `match=1` 확인  

검증이 끝나면 **반드시 다시 `0`/`false`로 내리거나**, C1~C6 전부 **사용자 승인 후에만** ON 유지.

### 1-3. 테스트용 등록 SQL이 있어야 함
discover는 `woo:testWooAiSql` 중 `@status='registered'` + `@plan_json`에 **값 있는 params**만 봅니다.

아래 “후보”에 해당하는 WKF가 **이미 등록**되어 있어야 합니다. 없으면:

1. Studio에서 해당 NL로 **생성 → 등록** (새 WKF 경로)  
2. 등록 후 다시 C 시나리오의 “질의”만 plan_only/찾기 로 실행  

| 후보 역할 | 예시 NL (등록해 둘 것) |
|---|---|
| 인천 여성 | `인천에 사는 여성 고객` |
| 서울 여성(연령 없음) | `서울 사는 여성 고객` |
| 서울 20대 여성(완전 동일용) | `서울 사는 20대 여성` |

## 2. 공통 조작 절차 (모든 C에 동일)

1. Studio 열기 (`v=155`, Option ON)  
2. intent가 있으면 **「기존 조건 찾아 쓰기」**(reuse) 선택 — Match OFF였을 때 숨겨졌던 UI가 ON이면 보임  
3. 왼쪽 입력란에 **그 C의 “질의 NL”** 입력  
4. **찾기 / 생성(plan_only 경로)** 실행 → 우측 **「값 대조 WKF」** 목록 확인  
5. 각 카드에서 확인:
   - 단정형 **「N개 중 M개 포함」문구가 없어야 함**
   - 조건마다 `라벨  질의값 = 후보값 (일치)` 또는 `= (없음)` 형태

## 3. 케이스별 합격 기준

### C1 — 서울 vs 인천 (완전 오탐 재현 차단)

| | 내용 |
|---|---|
| **질의** | `서울 사는 20대 여성` |
| **있으면 안 되는 후보** | 등록된 `인천에 사는 여성 고객` |
| **기대** | region(또는 거주 지역 fragment) **CONFLICT** → 인천 건이 **목록에 없음** |
| **실패** | 인천 건이 뜨거나 “포함”으로 단정 |

### C2 — 서울(연령만) vs 인천

| | 내용 |
|---|---|
| **질의** | `서울 사는 20대 고객` |
| **있으면 안 되는 후보** | `인천에 사는 여성 고객` |
| **기대** | region CONFLICT → 인천 건 **목록 제외** |
| **실패** | 예시2 사고처럼 인천이 “1개 중 1개 포함”으로 노출 |

### C3 — 부분 일치(연령만 후보에 없음)

| | 내용 |
|---|---|
| **질의** | `서울 사는 20대 여성` |
| **나와도 되는 후보** | `서울 사는 여성 고객` (서울·성별 같고 연령만 후보에 없음) |
| **기대** | 목록 **노출** · 대조표에 region/gender **일치**, age(또는 연령) **없음** |
| **실패** | 안 나오거나, 값 없이 “포함”만 표시 |

### C4 — 완전 동일 + 「동일」배지

| | 내용 |
|---|---|
| **질의** | `서울 사는 20대 여성` |
| **후보** | 예전에 **같은 조건으로 등록**한 WKF |
| **기대** | 전부 SAME + 가능하면 UI **「동일」** 배지 (`sqlContentHash` 일치) |
| **실패** | 동일 SQL인데 배지/정렬이 엉킴(보조). SAME 미표시면 실패 |

### C5 — Top-10 상한

| | 내용 |
|---|---|
| **준비** | 값 CONFLICT 없이 SAME≥1 인 등록 WKF가 **12건 이상** |
| **질의** | 그 조건들을 만족하는 NL 1건 |
| **기대** | 목록 **정확히 최대 10건** (11건 이상이면 실패) |
| **비고** | 환경에 12건이 없으면 **스킵 가능** — 체크리스트에 `C5 SKIP(데이터부족)` 기입 |

### C6 — 레거시(값 없음) 비노출

| | 내용 |
|---|---|
| **준비** | `@plan_json` 공란이거나 모든 `params`가 빈 registered 행 1건 이상(구 데이터) |
| **질의** | 아무 값 있는 조건 |
| **기대** | 그 레거시 WKF가 **상단/목록에 안 뜸** |
| **실패** | 값 없는 옛 건이 name만으로 매칭되어 노출 |
