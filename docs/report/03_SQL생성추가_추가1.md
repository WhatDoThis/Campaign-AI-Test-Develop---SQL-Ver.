
## 지금 뭐가 문제인가

현재 흐름을 따라가 보죠. 데이터가 없는 조건이 들어오면 Stage A에서 미매칭 → Foundry로 넘어감 → LLM이 스키마를 뒤짐 → 없음 → **그런데 여기서 LLM은 뭘 할까요?**

높은 확률로 **비슷해 보이는 컬럼을 찾아서 그럴듯한 SQL을 씁니다.** 이게 text2sql의 가장 잘 알려진 실패 모드예요. "해지 사유"를 요청했는데 스키마에 없으면 `status_cd`로 대충 만듭니다. 게이트는 통과합니다 — 컬럼 실재하고, 그레인 맞고, 건수도 그럴듯하니까요. 승인자는 "해지 사유 fragment"라는 라벨만 보고 승인하고요.

지금 시스템이 실패하면 큐가 `failed`로 떨어지고 `lastError`에 예외 메시지가 남을 뿐입니다. 마케터는 "왜 안 되는지" 모릅니다. **"데이터가 없어서 불가능"과 "일시적 오류"가 구분이 안 됩니다.** 이건 UX 문제가 아니라 신뢰 문제예요. 이유를 모르면 사용자는 표현만 바꿔서 재시도하고, 결국 언젠가 LLM이 그럴듯한 걸 만들어냅니다.

관련 연구를 보니 이게 학계에서도 별도 문제로 다뤄지고 있습니다. 상업용 text2sql 제품 실사용 로그 분석에서 **사용자 질문의 20%가 답변 불가**였다는 보고가 있고요. 20%는 예외가 아니라 주요 경로입니다.

---

## 조사에서 얻은 핵심 — 실패 유형을 나눠야 합니다

TriageSQL과 Query Carefully 연구가 답변 불가 질문을 유형별로 분류했는데, 여기서 실무적으로 중요한 발견이 있습니다. **유형마다 탐지 난이도가 극단적으로 다릅니다.**

Query Carefully 실측 기준으로 컬럼 자체가 없는 경우(Columns Missing)와 도메인 밖(Out of Domain)은 탐지 정확도가 거의 1.0에 가깝습니다. 반면 **값이 없는 경우(Values Missing)는 0.5, 컬럼 모호성은 0.3**입니다. 컬럼 모호성이 최악인 이유가 인상적인데, 논문 표현대로 "LLM이 그럴듯한 컬럼 하나를 골라 SQL을 생성하면서 모호함 자체를 인식하지 못하기" 때문입니다.

여기서 설계 결론이 나옵니다. **탐지 쉬운 건 LLM에 맡기고, 어려운 건 DB로 확인해야 합니다.**

컬럼 부재는 스키마만 보면 알 수 있으니 LLM 판정으로 충분합니다. 그런데 값 부재 — "Y요금제라는 값이 실제로 존재하는가" — 는 스키마를 아무리 봐도 모릅니다. **DB에 직접 물어봐야 합니다.** `SELECT DISTINCT plan_cd FROM ... LIMIT 50`을 실행해서 'Y'가 있는지 확인하는 거죠. 이게 지금 툴킷에 없는 기능이고, 추가해야 할 핵심입니다.

또 하나 실측 기반 팁이 있는데, 프롬프트에 **가능한 예시(answerable)를 넣는 게 불가능 예시보다 탐지율을 더 올렸습니다** (평균 0.49 vs 0.43). 둘 다 넣으면 0.8까지 갑니다. 직관과 반대라 기억해둘 만합니다.

---

## 설계 방향: 조기 판정 + 구조화된 불가 보고

핵심은 **Foundry에 들어가기 전에 막는 것**입니다. 지금은 LLM이 SQL을 쓰기 시작한 다음에야 문제가 드러나는데, 그 시점엔 이미 늦어요. 쓰기 시작한 LLM은 어떻게든 완성합니다.

그래서 Foundry 첫 단계를 SQL 생성이 아니라 **실현가능성 판정(Feasibility Triage)**으로 바꿉니다. 여기서 `feasible`이 나와야만 SQL 생성으로 넘어갑니다.

판정 유형은 6가지로 나눕니다. 데이터 자체가 없는 `no_data`, 컬럼은 있는데 값이 없는 `no_value`, DB 밖 지식이 필요한 `out_of_domain`, SQL로 표현 불가능한 `not_sql`, 여러 해석이 가능한 `ambiguous`, 그리고 진행 가능한 `feasible`. 각각 사용자에게 다른 메시지와 다른 다음 행동을 줍니다.

그리고 **`no_value`는 반드시 DB로 확인**합니다. LLM이 "값이 없는 것 같다"고 하면 `probe_values` 툴로 실제 DISTINCT 값을 뽑아 확인하고, 그 결과를 근거로 제시합니다. "plan_cd에 존재하는 값은 A, B, C, S이며 Y는 없습니다" — 이게 마케터가 납득할 수 있는 유일한 형태의 답변이에요.

---

## 근거 제시를 어떻게 신뢰할 것인가

여기서 조심할 게 하나 있습니다. LLM에게 "왜 불가능한지 설명해줘"라고 하면 **그럴듯한 거짓 근거**를 만들어낼 수 있습니다. 앞서 dedup에서 LLM 판정을 배제한 것과 같은 이유죠.

그래서 근거를 두 층으로 나눕니다.

**기계 근거(machine evidence)**는 실제 실행 결과입니다. 어떤 스키마를 뒤졌는지, 어떤 컬럼을 후보로 봤는지, DISTINCT 값 조회 결과가 무엇이었는지. 이건 툴 호출 로그에서 자동으로 수집됩니다. **반증 가능하고 재현 가능합니다.**

**서술 근거(narrative)**는 LLM이 그걸 한국어로 풀어 쓴 것입니다. 읽기 편하지만 그 자체로는 증거가 아닙니다.

UI에서는 서술을 먼저 보여주되, **"확인 근거" 섹션에 기계 근거를 항상 펼쳐볼 수 있게** 둡니다. 그리고 규칙 하나: **기계 근거가 없는 판정은 `ambiguous`로 강등**합니다. LLM이 "없습니다"라고만 하고 아무 툴도 안 돌렸으면 그건 판정이 아니라 추측이니까요.

---

## 사용자에게 뭘 돌려줄 것인가

"안 됩니다"로 끝나면 안 됩니다. 유형별로 **다음 행동**이 달라야 해요.

값이 없으면 실제 존재하는 값 목록을 보여주고 "혹시 이걸 의미하셨나요?"를 제안합니다. 모호하면 후보 컬럼 2~3개를 제시하고 선택하게 합니다 — 이게 재질의(clarification)고, 연구에서도 가장 효과적인 대응으로 꼽힙니다. 데이터 자체가 없으면 "수집 요청" 티켓으로 전환할 수 있게 하고요.

부분 성공도 중요합니다. 슬롯 3개 중 2개만 가능하면, **가능한 2개로 SQL을 만들되 "1개 조건이 제외되었음"을 명시적으로 경고**하는 옵션을 주세요. 다만 이건 기본값이 아니라 사용자가 명시적으로 선택해야 합니다. 조용히 조건을 빼먹는 게 제일 위험하니까요.

## X-2. new_ver/js/testWooFeasibility.js (신규 — 실현가능성 판정)
═══════════════════════════════════════════
`testWoo.feasibility.triage(slot, cfg)` → 판정 객체 반환.
**Foundry의 SQL 생성보다 반드시 먼저 실행된다.**

### verdict 6종
| verdict | 정의 | 다음 행동 |
|---|---|---|
| `feasible` | 스키마·값 모두 확인됨 | SQL 생성 진행 |
| `no_column` | 어떤 스키마에도 해당 개념의 컬럼 없음 | 불가 보고 + 유사 컬럼 제안 |
| `no_value` | 컬럼은 있으나 요청 값이 데이터에 없음 | 불가 보고 + 실제 값 목록 제시 |
| `out_of_domain` | DB 외부 지식 필요(경쟁사·외부지표 등) | 불가 보고 + 데이터 수집 안내 |
| `not_sql` | 집합 추출로 표현 불가(인과·예측·주관 판단) | 불가 보고 + 질문 재구성 안내 |
| `ambiguous` | 후보 컬럼/값이 복수, 또는 근거 불충분 | **재질의(clarification)** |

### 반환 계약
```
{
  slotId, verdict,
  confidence: "high|medium|low",
  narrative: "...",              // LLM 한국어 설명 (보조 정보)
  evidence: {                    // 기계 근거 (필수)
    schemasScanned: [...],
    columnsConsidered: [{schemaId, columnName, label, why}],
    valueProbes: [{schemaId, columnName, distinctCount, sampleValues:[...], requested, found:false}],
    toolCalls: N
  },
  alternatives: [                // 대안 제안
    {type:"column|value|rephrase", label:"...", detail:"...", schemaId, columnName}
  ],
  clarifyQuestion: "..."         // ambiguous일 때만
}
```

### 실행 절차
1) LLM에 슬롯 1건 + 툴 5종 제공. 시스템 프롬프트에 **No-Answer Rules** 명시:
   - "스키마에 근거가 없으면 SQL을 만들지 말고 verdict를 반환하라"
   - "비슷해 보이는 컬럼으로 대체 추론하지 말라. 대체 후보는 alternatives에만 넣어라"
   - "값 존재 여부는 추측하지 말고 반드시 probe_values로 확인하라"
2) **Few-shot 균형 배치** (문헌 실측: 가능+불가 예시 병행 시 탐지율 최대):
   - 가능(feasible) 예시 3건 + 불가 예시 3건(no_column/no_value/ambiguous 각 1)
   - 도메인 실제 사례로 구성. 골든셋에서 자동 추출 가능하게 설계
3) **증거 강등 규칙 (시스템 강제, LLM 무관)**:
   - `no_value` 인데 `evidence.valueProbes` 비어 있음 → `ambiguous`로 강등
   - `no_column` 인데 `evidence.columnsConsidered` 비어 있고 `search_columns` 미호출 → `ambiguous`로 강등
   - `feasible` 인데 `toolCalls === 0` → `ambiguous`로 강등
   - 강등 시 `confidence="low"`, narrative에 "근거 부족" 자동 부기
4) `feasible` 이어도 `confidence==="low"` 면 SQL 생성으로 넘기지 말고 `ambiguous` 처리
5) reasoning: `{enabled:false}`, `max_tokens:4096`, `response_format:{type:"json_object"}`
   (판정은 탐색이 아니라 분류 작업이므로 reasoning 불필요)

### X-5-1. Studio 결과 화면 — 불가 보고
- 슬롯별 카드 표시. 각 카드에:
  - 상단: 슬롯 원문 + verdict 배지(색상 구분) + confidence
  - 본문: `narrative` (한국어 설명)
  - **"확인 근거" 접기 섹션 (기본 접힘, 항상 존재)**:
    - 조회한 스키마 목록
    - 검토한 컬럼과 배제 사유
    - 값 조회 결과 — 예: "plan_cd의 실제 값(상위 50): A, B, C, S … 요청값 'Y' 없음"
    - 툴 호출 횟수
  - 하단: `alternatives` 를 클릭 가능한 칩으로. 클릭 시 해당 값/컬럼으로 NL 자동 수정 후 재요청
- **narrative와 evidence를 시각적으로 구분**한다.
  narrative에는 "AI 설명" 라벨, evidence에는 "실제 조회 결과" 라벨.
  근거 없는 서술을 사실로 오인하지 않게 할 것.
- `confidence==="low"` 카드는 "근거가 부족하여 확실하지 않습니다" 배너 표시.

### X-5-2. 재질의 화면 (ambiguous)
- `clarifyQuestion` 과 후보 선택지(라디오/체크박스) 표시
- 사용자 선택을 `clarifyAnswers`에 저장 후 해당 슬롯만 triage 재실행
- 재질의는 **슬롯당 최대 2회**. 초과 시 `infeasible` 확정
- 사용자가 "모르겠음" 선택 시 즉시 `infeasible` 처리(무한 루프 방지)

### X-5-3. 부분 실행 화면 (partially_infeasible)
- 가능/불가 슬롯을 좌우 분리 표시
- 가능한 슬롯만으로 만든 SQL 미리보기 + 예상 건수
- **경고 배너**: "요청하신 조건 중 N개가 제외되었습니다. 실제 대상은 의도보다 넓을 수 있습니다."
- 진행하려면 체크박스 확인 필수. 등록 후 목록에서 `hasExclusion` 아이콘 상시 표시

### X-5-4. 데이터 갭 대시보드 (testWooAiGapAdmin.jssp)
- `testWooAiGapLog` 를 `requestCount` 내림차순 표시
- 컬럼: 개념, verdict, 요청 횟수, 최초/최근 요청일, 상태
- 상태 변경(open→planned→resolved) 및 메모
- **활용 목적 명시**: 상위 항목 = 마케팅이 원하지만 데이터가 없는 것 = 데이터 수집 우선순위
