## 먼저, 업계가 이미 답을 냈습니다

재밌는 사실 하나. Databricks Unity Catalog의 공식 인증 태그 `system.certification_status`에는 값이 **딱 두 개**뿐입니다 — `certified`, `deprecated`. "승인 대기(pending)"라는 상태가 **아예 없어요**. 자산은 기본적으로 존재하고 사용 가능하며, 인증은 나중에 붙는 *신뢰 신호*일 뿐입니다. Looker의 content certification도 동일한 구조고요.

즉 성숙한 데이터 거버넌스 제품들은 전부 **승인을 게이트가 아니라 라벨로** 취급합니다. 지금 님 시스템만 승인을 write path에 blocking으로 걸어놓은 거예요. 그래서 병목이 생긴 게 맞습니다. 아이디어 방향은 옳습니다.

그런데 어제 받으신 조언과 제 결론이 **한 군데 크게 갈립니다.** 거기가 핵심이라 먼저 말씀드릴게요.

## 반대 지점: "near 중복만 사람에게" 는 틀린 트리거입니다

Snowflake Cortex Analyst의 Verified Query Repository(VQR)가 지금 님 SQL Fragment 라이브러리와 사실상 같은 물건입니다. NL 질문 ↔ 검증된 SQL 쌍을 모아두고, 유사 질문이 오면 그걸 근거로 SQL을 만들죠. 그런데 Snowflake가 "이건 사람이 봐야 한다"고 큐에 올리는 기준이 뭐냐면:

- **High frequency** — 비슷한 쿼리가 자주 등장함
- **Contains interesting semantic information** — 너무 단순한 건 제외
- **Novelty** — 기존 검증 쿼리와 안 겹침

한 번에 최대 10개씩만. 그리고 문서에 못 박아 뒀습니다. *"Suggestions are not automatically applied. Instead, Cortex Analyst uses suggestions as a queue of potential improvements."*

여기서 novelty는 "새로우니까 위험하다"가 아니라 **"이미 있는 거랑 겹치면 제안하지 마라"** 는 노이즈 제거 조건입니다. 실제 1순위 트리거는 **frequency**예요.

이게 왜 중요하냐면 — **near 중복은 검수 대상이 아니라 청소 대상**입니다. 배치가 조용히 병합하면 되는, 사람 눈이 전혀 필요 없는 일이에요. 반면 진짜 위험한 건 님도 이미 짚으신 "서울 ≠ 수도권" 유형, 즉 **게이트를 멀쩡히 통과하는 의미 오류**입니다. 문법 OK, 0건 아님, grain 맞음, 근데 뜻이 틀림. near dedup으로는 절대 못 잡습니다.

그러니까 검수 트리거는 이렇게 뒤집어야 합니다:

> **새로 만들어진 것을 보지 말고, 많이 쓰이는 것을 보라.**

Fragment 대부분은 한 번 쓰이고 죽습니다. 파레토가 아주 심하게 적용되는 영역이에요. 한 번 쓰고 버려질 fragment를 사람이 검수하는 게 지금 부담의 정체입니다. 반대로 20번 재사용되면서 200만 명짜리 딜리버리를 태우는 fragment는 — 그건 **사후에라도** 봐야 합니다. 그리고 그때는 이미 "유용함이 증명된" 소수라 검수할 값어치가 있고요.

이 한 줄 바꾸면 검수 대상이 생성량의 몇 %로 떨어집니다.

## 사람 대신 쓸 수 있는 자동 검증 카드

"그럼 의미 오류는 누가 잡냐" — 실은 사람 말고도 방법이 꽤 나와 있습니다.

**교차 모델 일치(cross-model consistency).** CM-SQL 논문이 서로 다른 모델(GPT-4o-mini + DeepSeek-V2.5)로 같은 NL을 SQL로 만들고 실행 결과를 대조해 BIRD dev에서 execution accuracy 65.65%를 냈습니다. N-rep consistency 쪽 연구도 CoT나 파인튜닝 없이 비슷한 수준을 훨씬 싸게 뽑고요. 님 구조에 대입하면: **같은 슬롯을 다른 모델로 한 번 더 생성해서 결과 카운트/키 집합을 비교**, 일치하면 자동 승격. 이게 "두 번째 사람 눈" 역할을 합니다. 슬롯당 LLM 호출 1회 추가면 되니 사람 대비 압도적으로 쌉니다.

**실행 피드백.** ExCoT 연구가 실행 결과를 학습·판정 신호로 쓰면 BIRD 57.37 → 68.51, Spider 78.81 → 86.59로 올랐다고 보고합니다. 님은 이미 `probe_sql` 게이트로 실행 기반 검증을 하고 있으니 방향은 맞게 잡으신 거예요. 여기에 **모집단 비율 sanity check**(추출 비율이 전체의 X% 초과/미만이면 자동 강등)만 얹으면 "서울 대신 수도권" 류의 상당수가 걸립니다. 완벽하진 않지만, 사람이 SQL 100개를 눈으로 훑는 것보다는 확실히 잘 잡습니다.

반대 근거도 솔직히 말씀드리면 — Vanna AI는 사용자가 question-SQL 쌍을 자유롭게 학습 데이터에 넣을 수 있는데, 커뮤니티에서 *"risk of injecting inaccurate training data"* 가 반복적으로 지적됩니다. 무검증 적재의 실패 사례가 실제로 있다는 뜻이에요. 그래서 "그냥 다 저장"은 안 되고, **게이트는 유지하되 사람만 빼는 게** 정답입니다.

## 제안 설계

**상태 모델 (4단계, Databricks 방식 차용)**

`draft` 는 게이트 실패, 검색 대상에서 제외. `active` 는 게이트 통과 시 **자동 진입하는 기본 상태**이고 즉시 사용 가능합니다 — 여기가 승인 제거의 핵심이에요. `certified` 는 교차 모델 일치, 또는 재사용 N회 이상 무사고, 또는 사람 승인 중 하나로 획득하며 Stage A 검색에서 상위 랭크됩니다. `deprecated` 는 큐레이터가 붙이고 검색에서 즉시 빠집니다.

중요한 건 **`certified`가 사용 조건이 아니라 랭킹 가중치**라는 점입니다. 인증 안 됐다고 못 쓰는 게 아니라, 인증된 게 있으면 그게 먼저 뽑히는 구조. Cortex Analyst가 VQR 없이도 답하지만 VQR이 있으면 그걸 우선 참조하는 것과 똑같습니다.

**큐레이터 배치 — 1시간은 과합니다**

말씀하신 스케줄러 아이디어는 좋은데 주기가 너무 짧아요. 공유 라이브러리에 대한 **mutation**이라 생성 경로와 동시성 충돌 위험이 있고, 1시간 안에 쌓이는 near 중복은 어차피 write-time dedup이 잡습니다. **일 1회 야간**이면 충분합니다.

그리고 이 배치의 진짜 킬러 기능은 병합이 아니라 **게이트 재실행(regression detection)** 입니다. Adobe Campaign 스키마는 계속 바뀝니다. 컬럼이 사라지거나 값 도메인이 변하면 어제까지 멀쩡하던 fragment가 조용히 0건을 뱉기 시작해요. 사람 승인은 이걸 **절대** 못 막습니다(승인은 생성 시점 1회뿐이니까). 반면 야간 재실행은 잡습니다. 승인제를 없애면서 오히려 안전성이 올라가는 지점이 여기예요. 이 논거 하나면 이해관계자 설득 끝납니다.

**절대 하드 삭제 금지 — 이건 강하게 말씀드립니다**

Fragment는 이미 배포된 워크플로우/딜리버리가 참조하고 있을 수 있습니다. 큐레이터가 중복이라고 지워버리면 그날 밤 운영 장애입니다. 반드시 **tombstone + `supersededBy` 별칭 리다이렉트**로 가세요. 병합은 "삭제 후 통합"이 아니라 "구 키가 신 fragment로 해석되도록 alias 추가"입니다. Feast 같은 피처 스토어들이 하위호환 정책을 그렇게 운영하는 이유고, 관련 글에 이런 문장도 있더군요 — *"피처 스토어의 첫 산출물은 새 피처가 아니라 기존 중복 피처 3개의 deprecation이다."* 님 라이브러리도 똑같은 운명입니다.

미사용 판정 기준은 Looker가 쓰는 **90일 미조회**를 그대로 빌리면 됩니다. 바퀴 다시 만들 필요 없어요.

**사람이 남아야 하는 딱 두 곳**

첫째, **민감 컬럼 참조 fragment는 blocking 승인 유지.** 수신거부, 마케팅 수신동의, 개인식별 관련 컬럼을 건드리는 fragment는 자동 활성화하면 안 됩니다. PIPA 이슈이기도 하고 여기서 사고 나면 시스템 전체 신뢰가 날아갑니다. 대신 이건 **컬럼 allowlist 기반**이라 전체 생성량의 극소수예요. 부담이 안 됩니다.

둘째, **월 1회 다이제스트.** 큐레이터가 뽑은 상위 빈도 미인증 fragment 10개 + 병합 제안 + deprecate 예정 목록. Cortex가 한 번에 10개씩만 제안하는 걸 그대로 따라가세요. 검토 대상이 10개면 사람이 30분에 끝냅니다.

**그리고 킬 스위치.** 승인 게이트를 뺄 때 정치적으로 반드시 필요한 대가입니다. 특정 fragment를 원클릭으로 `deprecated` 전환 → 즉시 검색 제외 + 그걸 참조한 워크플로우 목록 조회. "사고 나면 3초 안에 끌 수 있다"가 보장되면 사전 승인 없애는 걸 아무도 반대 못 합니다.

## 결정적 논거: 비용 곡선

이 얘기를 마지막에 하는 이유는, 이게 님이 위에 보고할 때 쓸 한 문장이라서입니다.

사전 승인 비용은 **O(생성량)** 입니다. 시스템이 성공할수록 커집니다. AI를 잘 쓸수록 사람이 더 갈립니다. 구조적 모순이죠.

큐레이션 비용은 **O(라이브러리 크기)** 이고, 라이브러리는 dedup 때문에 **포화**합니다. 조직이 묻는 조건의 종류는 유한하니까요. 즉 시간이 지나면 비용이 평평해집니다.

님이 느끼시는 "AI 쓰려고 인력이 더 든다"는 감각은 착각이 아니라 **비용 곡선을 잘못 고른 결과**입니다.
