## N-1 (P0) getIfExists 반환 파싱 오류 — 큐 처리 전면 불능

### 문제
`getIfExists`는 컬렉션이 아니라 **단일 엘리먼트 자체**를 반환한다(무매치 시 빈 엘리먼트).
`select`만 `<xxx-collection>`으로 감싼다. 현재 코드는 `res.testWooAiRequestQueue[0]` 로
자식 컬렉션처럼 접근 → E4X 빈 XMLList → `[0]` undefined → `r.@id` 예외.

### 대상
- `new_ver/js/testWooFoundry.js` → `_getQueue(id)`
- `new_ver/js/testWooLifecycle.js` → `_getFragmentById(id)`
- 레포 전체에서 `operation="getIfExists"` 를 grep 하여 동일 패턴 전수 교정

### 수정 규칙
1. 존재 판정은 `if (String(res.@id || "") === "") return null;`
   (`.length` / `[0]` / `res.<schemaRoot>` 접근 전면 금지)
2. `res` 자체를 행 객체로 읽는다. 예:
   ```js
   var res = q.ExecuteQuery();
   if (String(res.@id || "") === "") return null;
   return {
     id: Number(res.@id),
     nl_text: String(res.@nl_text),
     status: String(res.@status),
     attempt_count: Number(res.@attempt_count) || 0
     // ... 나머지 필드 동일 패턴
   };
   ```
3. `getIfExists` 쿼리의 `<select>` 에 `<node expr="@id"/>` 를 **반드시 명시**한다.
   - `_getFragmentById` 는 현재 `@id` 미선택 상태 → 추가 (N-6 동시 해소).
     `revoke` / `hardDelete` 가 이 값에 의존한다.
4. `_claimQueue` 의 재조회 검증도 `_getQueue` 를 경유하므로 별도 수정 불필요.
   단, 수정 후 선점 검증 로직이 정상 동작하는지 재확인.

### 부수 수정 (오진 방지)
`testWooFoundry.js` `_isSchemaError(e)` 가 너무 느슨하다.
현재 `msg.indexOf("unknown") >= 0` 때문에 일반 JS 오류까지 "스키마 배포 미선행"으로
치환되어 원인 추적을 방해한다.
→ **`XTK-170` / `XTK-171` 접두사 매칭만 남기고** `"does not exist"`, `"unknown"` 조건 제거.
→ 스키마 오류가 아닌 예외는 원본 메시지 그대로 전파.

## N-2 (P0) Schema 객체에 toXMLString 없음 — 스키마 조회 전부 조용히 0건

### 문제
`application.getSchema()` 는 **Schema 클래스** 객체를 반환하며 공식 메서드는 `toDocument` 뿐이다.
`toXMLString` 은 DOMElement 메서드다. 현재 `new XML(String(sch.toXMLString()))` 는 즉시 예외.
`_toolDescribeSchema` / `_toolSearchColumns` 가 예외를 삼키고 있어(`catch (eSch) {}`)
증상이 "에러"가 아니라 **"모든 스키마 조회 0건"** 으로 나타나고,
Triage가 근거 없이 `no_column` / `ambiguous` 를 내는 거짓 판정으로 이어진다.

### 대상
`new_ver/js/testWooToolkit.js` → `_schemaXml(schemaId)`

### 수정
```js
function _schemaXml(schemaId) {
  var sch = application.getSchema(schemaId);
  if (!sch) throw new Error("schema not found: " + schemaId);
  var doc = sch.toDocument();              // → DOMDocument
  return new XML(doc.documentElement.toXMLString());  // DOMElement 메서드로 호출
}
```
- `_schemaXml` 을 경유하는 `describe_schema`, `search_columns`, `_resolveSqlTable` 전부 재확인.
- 레포 전체에서 `.toXMLString()` grep → **호출 대상이 DOMElement 인지** 각각 확인.
  Schema / DOMDocument 에 직접 호출한 지점이 있으면 전부 교정.

### 조용한 실패 제거 (필수)
- `_toolSearchColumns` 의 `catch (eSch) {}` 빈 블록 금지.
  → `logWarning("[testWoo.toolkit.search_columns] schema load failed: " + schemaId + " / " + String(eSch.message || eSch));`
- `_toolDescribeSchema` 동일 처리.
- 스키마 로드가 1건도 성공하지 못한 경우 결과에 `{schemaLoadFailed:true}` 를 실어
  Triage 가 이를 `ambiguous` 근거로 삼되 `no_column` 판정은 내리지 못하게 한다.

## N-3 (P1) 물리 컬럼명 추정 금지 규약화

### 배경
SQL 필드명은 `sqlname` 미지정 시 **타입 접두사 + 이름** 으로 자동 생성된다
(string→`s`, integer→`i`, double→`d`, datetime→`ts`).
본 프로젝트 스키마는 `status`, `attempt_count` 등 스네이크 표기라
실제 물리명(`sStatus` / `sstatus` / `s_status`)이 ACC 버전·DBMS에 따라 달라진다.

### 조치
- 이미 적용된 "queryDef 카운트" 방식을 유지하고 되돌리지 말 것.
- `docs/report/01_개발가이드.md` 섹션 6에 규약 신설:
  **"woo:* 커스텀 스키마에 대한 물리 컬럼명 추정 SQL 금지.
    카운트/존재확인은 queryDef(operation="count") 를 사용한다.
    sqlSelect/sqlGetInt 의 직접 대상은 검증된 표준 스키마 테이블 또는
    LLM이 생성하고 probe 를 통과한 fragment SQL 로 한정한다."**
- 성능 사유로 `sqlGetInt` 로 되돌리려는 시도를 차단하는 주석을 해당 함수 상단에 남길 것.

## N-4 (P2) dial.limit 이중 서브쿼리 + 샘플 비결정성

### 문제
`testWooProbe.run` 샘플 경로가
`SELECT * FROM (SELECT kc AS tw_key FROM (inner) tw_sample) tw_lim LIMIT n` 로 3중 중첩.
`_toolProbeValues` 는 `inner` 에 이미 `DISTINCT` 가 있어 한 겹 더 쌓인다.
Oracle `FETCH FIRST` / MSSQL `TOP` 은 `ORDER BY` 미지정 시 결과가 비결정적이라
`auditSample` 이 재현되지 않는다(승인 화면의 근거 자료이므로 재현성 필수).

### 수정
- `new_ver/js/testWooProbe.js` `dialect().limit(sql, n)` 에 결정적 정렬 부여:
  래핑 시 `ORDER BY 1` 을 포함한다. Oracle 은 `ORDER BY 1 FETCH FIRST n ROWS ONLY`,
  MSSQL 은 `SELECT TOP n * FROM (...) tw_lim ORDER BY 1`, 그 외 `ORDER BY 1 LIMIT n`.
- 불필요한 중첩 한 겹 제거: `run()` 에서 `sampleInner` 를 만들 때
  이미 서브쿼리이므로 `dial.limit` 가 다시 `SELECT * FROM (...)` 로 감싸지 않도록
  `limit(sql, n, alreadyWrapped)` 형태로 분기하거나, 래핑 지점을 한 곳으로 통일.
- 회귀 확인: 동일 fragment 를 2회 probe 했을 때 `sample` 배열이 동일해야 한다.

## N-5 (P2) used_fragments 부분 문자열 매칭 오탐

### 문제
`listImpact` 의 `uf.indexOf(needle) >= 0`,
`revoke` 의 `... || uf.indexOf(f.name) >= 0` 때문에
`sub__customer__joined__recent` 조회 시 `sub__customer__joined__recent_v2` 가 매칭되어
무관한 SQL이 `affected` 로 마킹된다.

### 수정
- `used_fragments` 는 JSON 배열이므로 **파싱 후 원소 정확 비교**로 전환.
  ```js
  function _usesFragment(usedFragmentsJson, name) {
    var arr;
    try { arr = JSON.parse(String(usedFragmentsJson || "[]")); } catch (e) { arr = []; }
    if (Object.prototype.toString.call(arr) !== "[object Array]") return false;
    for (var i = 0; i < arr.length; i++) {
      var it = arr[i];
      var n = (it && it.name != null) ? String(it.name) : String(it);
      if (n === String(name)) return true;
    }
    return false;
  }
  ```
- `listImpact`, `revoke` 양쪽에서 이 헬퍼만 사용.
- `revoke` 의 `indexOf` 기반 OR 뒷항(`|| uf.indexOf(f.name) >= 0`) **삭제**.
- JSON 파싱 실패 레코드는 `impact_status="unknown"` 으로 마킹하고 로그 남길 것(무시 금지).

## S-1 (신규) 배포 직후 스모크 스크립트 추가

### 배경
`tools/checkRhinoSyntax.js` 는 구문 오류는 잡지만 **API 시그니처 오용은 못 잡는다**.
N-2가 정확히 그 사각지대(문법 정상 + 존재하지 않는 메서드 호출)였다.

### 요구사항
`new_ver/tools/testWooSmoke.js` 신규 작성. ACC 워크플로우 JS 액티비티에 붙여
배포 직후 1회 실행하는 용도. Rhino 제약 준수(var / for / 화살표함수 금지).

포함 항목:
1. 각 라이브러리 `loadLibrary` 후 전역 정의 확인
   (`testWoo.probe/toolkit/llm/fragments/lifecycle/dedup/gates/feasibility/foundry/compiler`)
   — 하나라도 undefined 면 즉시 실패 로그.
2. `testWoo.probe.preflight()` → `ok:true` 확인.
3. `sqlSelect("row,@x:string", "SELECT 1 AS x")` 결과를 `logInfo` 로 출력(XML 구조 확정용).
4. `testWoo.toolkit.invoke("describe_schema", {id:"nms:recipient"})`
   → 속성 배열이 **비어 있지 않은지** 확인. 비어 있으면 N-2 재발로 간주하고 실패.
5. `testWoo.toolkit.invoke("search_columns", {keyword:"email"})`
   → 1건 이상 매칭 확인. 0건이면 실패.
6. 큐 더미 1건 insert → `_getQueue` 경유 조회 → 필드 일치 확인 → 삭제.
   (N-1 회귀 검출용. getIfExists 파싱이 깨지면 여기서 즉시 드러남)
7. 각 항목 PASS/FAIL 을 `logInfo` 로 요약 출력, 실패 1건 이상이면 마지막에 `logError`.

### 규칙
- 스모크는 **읽기 위주**. 6번 더미 레코드는 반드시 정리(finally 에서 삭제).
- 고객 실데이터 출력 금지.
- `docs/report/01_개발가이드.md` 에 "배포 절차 마지막 단계 = 스모크 실행" 명시.
