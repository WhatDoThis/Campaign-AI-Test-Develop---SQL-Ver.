## 2. 자가진단 알고리즘 (요청하신 프롬프트)

원인 추정을 그만두고 판정 절차로 바꾸기 위해, 아래 알고리즘을 만들어 저 자신에게 돌렸습니다. 재사용 가능한 템플릿이라 그대로 보관하셔도 됩니다.

```
[LLM 에이전트 단계 실패 근원 판정 알고리즘 v1]
입력: 실패 지점 함수 F, 실패 메시지 M, 관련 프롬프트 P, 소비자 코드 C

A. 계약 존재성
   A1. C가 읽는 필드 전체를 열거하라.
   A2. P가 그 필드를 명시하는가?  아니면 → 근원 = 계약 부재. (다른 가설 검사 중단)
   A3. C가 강제하는 제약(정규식/게이트/파서)을 열거하라.
   A4. P가 그 제약을 명시하는가?  아니면 → 근원 = 제약 미고지.

B. 종료 조건 정합성
   B1. 루프가 "끝났다"고 판단하는 조건 L을 쓰라.
   B2. P가 모델에게 알려준 종료 시점 L' 을 쓰라.
   B3. L ≠ L' 이면 → 근원 = 종료 조건 불일치.

C. 상태 재사용 안전성
   C1. 재시도 시 재사용되는 상태 S가 있는가?
   C2. S가 프로토콜상 불완전할 수 있는 경로가 있는가? (예: 응답 없는 tool_calls)

D. 예외 경로
   D1. 재시도 루프 "안"에서 던져지는 예외가 루프를 무력화하는가?

E. 자원 회계
   E1. 예산 리셋 단위와 소비 단위가 같은가? 다르면 후단 단계가 굶는가?

F. 관측 가능성
   F1. 이 경로를 사람 개입 없이 60초 내 재현할 수단이 있는가?
        없으면 → 어떤 수정도 "한 번에 하나씩"만 검증되어 연쇄가 발생한다.
```

## 3. 알고리즘 실행 결과 (실제 코드 대조)

**A. 계약 존재성 — 여기서 즉시 걸립니다. 이게 근원입니다.**

`_fragDocFromLlm`이 읽는 필드는 `frag.name`, `frag.label`, `frag.tags`, `frag.keyColumn`, `frag.scopeKey`, `frag.sqlText`, `frag.params[].name/type/domain`, `frag.description`, `frag.rationale` — 9종입니다.

그런데 `_foundrySystemPrompt()` 전문을 보면:

```
"Output ONE fragment per request as JSON only on the final turn."
"name pattern: {domain}__{entity}__{predicate}__{qualifier}"
"scopeKey: sub-entity grain or null string for recipient-level."
```

**JSON 스키마가 어디에도 없습니다.** `sqlText`라는 키 이름을 모델은 알 방법이 없어요. Pass0·Pass1·Triage 프롬프트에는 전부 `OUTPUT JSON ONLY: {…}` 로 정확한 형태가 박혀 있는데, **정작 가장 복잡한 산출물인 Foundry 생성 프롬프트만 빠져 있습니다.** `FINAL_TURN_NUDGE`도 "Output the fragment JSON now"라고만 하고 형태를 안 줍니다.

A4도 마찬가지로 실패합니다. 게이트가 강제하는 제약이 프롬프트에 하나도 없습니다.

| 코드가 강제 | 위치 | 프롬프트 고지 |
|---|---|---|
| SELECT 리스트 = grain 컬럼 **단 하나** | `_checkSelectIsGrain` | ❌ |
| `WITH` 로 시작 금지 | `fragmentSqlContract` | ❌ |
| 세미콜론·큰따옴표·`{{param}}` 금지 | `g1Syntax` | ❌ |
| `total === distinctKey && nullKey === 0` | G-B | ❌ |
| 이름 `^[a-z0-9]+__…$` (소문자, 1·2세그먼트에 `_` 불가) | G-F | 패턴만, 문자셋 ❌ |

즉 모델은 눈을 가린 채 6개의 게이트를 통과하라는 요구를 받고 있습니다. 3번 재시도해서 통과할 확률이 낮은 게 당연합니다.

**B. 종료 조건 불일치 — 두 번째 근원.**

프롬프트: *"JSON only **on the final turn**"* → 모델은 "아직 마지막 턴 아니니까 JSON 내면 안 되겠군"으로 읽습니다.
코드: `runToolLoop`은 **툴 호출이 없는 첫 턴에 즉시 return** 합니다.

그래서 모델이 3턴째에 조사를 끝내고 *"조사 완료했습니다. 이제 fragment를 만들겠습니다"* 같은 평문을 내면 → 루프 종료 → `_parseFragmentJson`이 `{` 를 못 찾음 → **정확히 `fragment JSON missing`**. #89에서 관측된 증상과 완전히 일치합니다. 강제 턴은 6턴째에만 걸리는데, 루프는 3턴째에 이미 나가버렸으니 강제 장치가 발동조차 안 합니다.

**C·D. 재시도 무력화 — 왜 3번 시도가 1번처럼 끝나는가.**

`_parseFragmentJson`은 게이트 재시도 루프 **안에서 throw** 합니다. `generateFragmentForSlot`에 catch가 없으니 예외가 `processQueueItem`까지 튀어 `gateRetries: 2`가 통째로 무의미해집니다. JSON 파싱 실패는 정확히 "되먹임으로 고칠 수 있는" 부류인데 재시도 기회 없이 죽습니다.
추가로 `messages`를 재시도 간 재사용하는데, 마지막 턴에 tool_calls가 섞이면 응답 없는 tool_calls가 히스토리에 남아 다음 호출이 400으로 거절됩니다(잠복).

**E. 예산 회계 — 다음에 터질 지뢰.**

`resetRequest()`는 **요청당 1회**인데 `totalCallBudget: 20`입니다. 슬롯 1개 기준 Triage 최대 5콜 + 생성 3시도 × 5콜 = 20. **딱 소진.** 슬롯이 2개면 두 번째 슬롯의 생성 단계는 `probe_sql`이 전부 `budget exceeded`로 막혀 모델이 검증 없이 SQL을 내고 게이트에서 죽습니다. F-0을 고치면 바로 이게 다음 얼굴로 나타납니다.

**F. 관측 가능성 — "연쇄"의 진짜 정체.**

이 경로를 돌리려면 Studio 입력 → 큐 적재 → WF 배치 5분 대기가 필요합니다. 스모크는 pass0/embedding까지만 커버하고 **생성 루프는 한 줄도 안 탑니다.** 그래서 한 사이클에 결함 하나씩만 노출됩니다. 답답하신 게 정상입니다. 코드가 나쁜 게 아니라 **계측기가 없는 것**이고, 이건 F-5 하나로 끝납니다.

- **F-0 (P0)** 생성 프롬프트에 fragment JSON 스키마 + 게이트 규칙 전문을 명시

## F-0 (P0) 생성 프롬프트에 출력 계약 명시
`_foundrySystemPrompt()` 는 `_fragDocFromLlm` 이 읽는 필드를 한 개도 명시하지
않는다(sqlText/keyColumn/scopeKey/params 등). 게이트 규칙도 전부 미고지다.

- `_foundrySystemPrompt()` 에 아래를 **정확한 문자열로** 추가:
  * 출력 스키마 (예시 포함, 코드의 `_fragDocFromLlm` 과 1:1 대응):
    {"name":"woo__customer__region__seoul","label":"서울 거주 고객",
     "description":"...","keyColumn":"sCustomer_id","scopeKey":"",
     "tags":["region"],"params":[],
     "sqlText":"SELECT DISTINCT sCustomer_id FROM testWooSampleCustomer WHERE sRegion = '서울'",
     "rationale":"..."}
  * SQL 규칙 (게이트 코드에서 그대로 도출 — 문구를 임의로 줄이지 말 것):
    - SELECT 리스트는 keyColumn **단 하나**. 콤마·추가 컬럼·`*` 금지 (_checkSelectIsGrain)
    - `WITH` 로 시작 금지 (fragmentSqlContract)
    - 세미콜론 금지 · 큰따옴표 식별자 금지 · `{{param}}` 잔존 금지 · DDL/DML 금지 (g1Syntax)
    - grain 은 중복·NULL 이 없어야 한다 → 필요하면 `SELECT DISTINCT` (G-B)
    - 결과 0건이면 실패 (G-C)
    - 테이블·컬럼은 **물리명만** (describe_schema 의 sqlColumn / sqltable)
  * name 규칙: 소문자·숫자만, `__` 4세그먼트 이하, **1·2 세그먼트에는 `_` 불가**
    (정규식 `^[a-z0-9]+__[a-z0-9]+__[a-z0-9_]+(__[a-z0-9_]+)?$`)
  * scopeKey: recipient 단위면 빈 문자열 `""` (null 아님)
  * params 는 배열 `[{"name":"...","type":"string|number","domain":[...]}]`, 없으면 `[]`
- `FINAL_TURN_NUDGE` 에도 "Output the JSON object matching the schema above" 를 명시.
- `params` 를 객체로 받아도 죽지 않도록 `_fragDocFromLlm` 에 배열/객체 양쪽 처리 추가.
- `_fragDocFromLlm` 진입 시 필수 필드(name/keyColumn/sqlText) 누락을 즉시 판정하고
  누락 키 목록을 담은 오류를 던진다(아래 F-2 의 되먹임 재료가 된다).

## F-1 (P0) 루프 종료 조건을 프롬프트와 일치시킨다
프롬프트는 "final turn 에만 JSON" 이라 지시하는데 `runToolLoop` 은 **툴 호출이
없는 첫 턴에 즉시 return** 한다. 모델이 "조사 끝났습니다" 평문을 내면 그대로
빠져나와 `fragment JSON missing` 이 된다.

- `runToolLoop` 에 선택 인자 `opts.requireJson`(기본 false) 추가.
  true 이면 툴 호출이 없는 턴에서 `content` 에 `{ … }` 가 없을 때 **return 하지 않고**
  `{role:"user", content:"…JSON 을 지금 출력하라(스키마 재고지)…"}` 를 msgs 에 push 후 다음 턴 진행.
  남은 턴이 없으면 그때 예외.
- `generateFragmentForSlot` 은 `requireJson:true` 로 호출한다.
- tool_calls 판정을 `finish_reason` 에 의존하지 말 것:
  조건을 `msg.tool_calls && msg.tool_calls.length` 우선으로 바꾸고
  `finish_reason` 은 로그에만 남긴다(Gemini 가 "stop" 으로 내려보내는 경우가 있다).
- 턴 로그에 `hasJson=true/false` 를 추가한다.

## F-2 (P0) JSON 파싱 실패도 게이트 재시도 대상으로
`_parseFragmentJson` 이 게이트 재시도 루프 **안에서** throw 해 `gateRetries:2` 가
통째로 무력화된다. JSON 형태 오류야말로 되먹임으로 고쳐지는 부류다.

- `generateFragmentForSlot` 의 attempt 루프에서 `_parseFragmentJson` 과
  `_fragDocFromLlm` 을 try/catch 로 감싼다.
- 실패 시 `_gateFeedback` 과 같은 형식의 `_shapeFeedback(err)` 메시지를
  `role:"user"` 로 push 하고 **다음 attempt 로 계속**한다(즉시 throw 금지).
  메시지에는 누락/오인식 키 목록과 스키마 예시를 다시 싣는다.
- 모든 attempt 소진 시에만 `{fragDoc:null, gate:lastGate, shapeError:…}` 반환.
- 반환 객체에 `shapeError` 를 추가하고 `processQueueItem` 의 실패 `last_error` 에 포함.

## F-3 (P1) 재시도 간 messages 재사용 안전화
- 매 attempt 시작 시 `msgs` 를 훑어 **대응하는 role:"tool" 응답이 없는
  assistant.tool_calls 메시지**가 있으면 해당 tool_calls 를 제거하거나
  더미 tool 응답(`{"error":"not executed"}`)을 채워 프로토콜을 정합화한다.
  (미응답 tool_calls 가 남으면 다음 요청이 400 으로 거절된다)
- attempt 2 이상에서는 히스토리를 압축한다: system + 최초 user + 마지막 assistant 본문
  + 되먹임 메시지만 유지(툴 왕복 전체 재전송 금지, 토큰·지연 절감).
- assistant 메시지는 응답 객체를 **그대로** push 할 것(`reasoning_details` 보존).
