## 2. 알고리즘 재실행 — 새 결함

**C. 상태 재사용 안전성 → C-1 (P0)**

```js
if (attempt > 0) {
  _sanitizeToolHistory(messages);      // ① 더미 tool 응답을 messages 끝에 push
  messages = _compressForRetry(messages); // ② system+firstUser+lastAssistant+lastUser만 남김
}
```

①이 push한 더미 `role:"tool"` 메시지를 ②가 **전부 버립니다.** 그런데 `_compressForRetry`가 남기는 `lastAssistant`는 `slim`으로 만들 때 `tool_calls`를 제거하니 결과적으로 괜찮아 보이지만 — **`lastUser`가 문제입니다.** attempt 1에서 `_gateFeedback`을 push한 뒤 attempt 2로 오면, `lastAssistant`가 tool_calls를 가진 원본일 때 `_compressForRetry`는 `slim`으로 정리하지만, 그 뒤 `runToolLoop`이 다시 tool_calls를 쌓고 **마지막 턴에서 `tool_choice:"none"`으로 끝나면 미응답 tool_calls가 남은 채** attempt 3의 압축이 `lastAssistant`만 보고 중간 것들을 버립니다. 즉 순서가 뒤집혀야 합니다: **압축 먼저, 정리 나중.** 그리고 `_sanitizeToolHistory`는 더미를 배열 **끝**에 push하는데, OpenAI 호환 규약상 `tool` 메시지는 대응 `tool_calls` **직후**에 와야 합니다. 끝에 몰아넣으면 순서 위반으로 400이 납니다.

**E. 자원 회계 → E-1 (P1)**

`generateFragmentForSlot`은 `setPhaseBudget("generate")`를 **함수 진입 시 1회**만 호출합니다. 그런데 `_phaseCalls`는 `setPhaseBudget`에서만 0이 됩니다. 슬롯이 2개면 두 번째 슬롯의 triage가 `setPhaseBudget("triage")`로 리셋 → 다시 generate로 리셋되므로 슬롯별로는 정상입니다. **진짜 문제는 반대쪽**입니다: `totalCallBudget: 40`인데 슬롯당 최대 `triage 12 + generate 24 = 36`. **슬롯 2개면 두 번째 슬롯은 4콜만 쓰고 전부 막힙니다.** `maxNewFragments: 3`이라 슬롯 3개까지 상정하는데 예산은 1개분입니다. #92가 슬롯 1개짜리라 안 걸린 것뿐입니다.

**E-2 (P2)**: `_reasoningBudget(16384)` = 4096이 매 턴 요청됩니다. 6턴 × 3 attempts = 최대 18회. `foundryMaxTokens: 16384`는 턴당 상한이지 누적 상한이 아니라 `tokenBudget: 60000`을 훨씬 초과할 수 있는데, **`tokenBudget`/`dailyBudget`은 어디서도 검사되지 않습니다** (env 주석에 "부분 미적용"이라 솔직히 적혀 있긴 합니다). #92에서 슬롯 1개 4043토큰이었으니 3슬롯 × 3attempts면 3.6만 토큰까지 갑니다.

**F. 관측 가능성 → F-6 (P1)**

스모크 9번은 `forceGenerate:true` + **슬롯 1개**만 검증합니다. C-1(재시도 2회차)과 E-1(슬롯 2개 예산)은 **둘 다 스모크가 안 밟는 경로**입니다. 즉 지금 계측기는 "1회 성공"만 보증하고 "실패 후 복구"는 보증하지 않습니다. #92가 `attempts=1`로 통과한 건 좋은 소식이지만, 동시에 **F-2·F-3이 한 번도 실행되지 않았다**는 뜻이기도 합니다.

**A·B 재점검 → A-1 (P2)**

`_foundrySystemPrompt`에는 `probe_sql`로 검증하라는 지시가 있지만, 게이트 G-B(`total === distinctKey && nullKey === 0`)가 **`probe_sql`의 반환 필드명과 다른 이름**으로 설명돼 있습니다. 프롬프트는 "Grain must be unique and non-NULL"이라고만 하고, 모델이 `probe_sql` 결과의 어느 필드를 봐야 자가검증되는지 알려주지 않습니다. #92는 통과했지만 재시도 시 모델이 무엇을 고쳐야 할지 판단할 근거가 약합니다.

## C-1 (P0) 재시도 히스토리 정리 순서가 뒤집혀 있다
`generateFragmentForSlot` attempt>0 블록:
  _sanitizeToolHistory(messages)  → 더미 tool 응답을 배열 **끝**에 push
  messages = _compressForRetry(messages) → 그 더미를 전부 버림
두 가지가 동시에 잘못됐다.
 (1) 순서: 정리 → 압축이라 정리 결과가 폐기된다. 압축 → 정리여야 한다.
 (2) 위치: OpenAI 호환 규약상 role="tool" 은 대응 tool_calls **직후**에 와야 한다.
     배열 끝에 몰아넣으면 순서 위반으로 400 이 난다.

- `_sanitizeToolHistory` 를 **삽입 위치 보정형**으로 재작성:
  * 배열을 순회하며 assistant.tool_calls 를 만나면, 그 직후 위치에서 대응하는
    role="tool" 메시지가 있는지 확인하고, 없는 id 에 대해 **바로 그 자리에**
    `{role:"tool", tool_call_id:id, content:'{"error":"not executed"}'}` 를 splice 삽입한다.
  * 배열 끝 일괄 push 방식은 제거한다.
- 호출 순서를 **`_compressForRetry` → `_sanitizeToolHistory`** 로 교체한다.
- `_compressForRetry` 는 이미 lastAssistant 를 tool_calls 없는 slim 으로 만들므로
  압축 경로에서는 정리가 no-op 이 되는 것이 정상이다. 그래도 방어적으로 호출한다.
- `runToolLoop` 정상 반환 직전에도 `_sanitizeToolHistory(msgs)` 를 1회 적용해
  루프를 빠져나온 messages 가 항상 프로토콜 정합 상태이도록 한다.

## E-1 (P0) totalCallBudget 이 슬롯 1개분밖에 없다
슬롯당 최대 = triageCallBudget(12) + generateCallBudget(24) = 36.
totalCallBudget 은 40 이므로 **두 번째 슬롯은 4콜만 쓰고 전부 차단**된다.
maxNewFragments 는 3 이라 슬롯 3개를 상정하는데 예산은 1개분이다.
#92 는 슬롯 1개라 노출되지 않았다.

- `testWooEnv.js` toolkit 블록 재산정:
  * `totalCallBudget: 40` → **`120`** (= 슬롯 3개 × 36 + 여유 12)
  * 주석에 산출식을 명시: `maxNewFragments × (triageCallBudget + generateCallBudget) + 여유`
  * `probeSqlBudget: 8` → **`18`**, `probeValuesBudget: 6` → **`14`**,
    `searchColumnsBudget: 8` → **`18`** (이들도 요청 단위 누적이라 슬롯 2개째에 굶는다)
  * 각 항목 주석에 "요청 단위 누적이며 슬롯 수에 비례해야 한다" 를 적는다.
- `testWooToolkit.js` 의 하드코딩 기본값(TOTAL_BUDGET 등)도 동일 값으로 맞춘다.
- `invoke` 의 total 초과 메시지에 현재 phase 와 누적 콜 수를 함께 실어
  "어느 슬롯에서 굶었는지" 를 저널에서 바로 알 수 있게 한다.
  예: "tool call budget exceeded (total 120, used=120, phase=generate:m1)"

## E-2 (P1) tokenBudget / dailyBudget 이 선언만 되고 검사되지 않는다

## A-1 (P2) 게이트 자가검증 방법을 프롬프트가 알려주지 않는다
프롬프트는 "Grain must be unique and non-NULL" 이라고만 하고, probe_sql 반환의
어느 필드로 그것을 확인하는지 알려주지 않는다. 재시도 시 무엇을 고쳐야 하는지
모델이 판단할 근거가 약하다.

- `_foundrySystemPrompt` 의 SQL RULES 에 자가검증 절차를 1줄 추가:

- `_gateFeedback` 에도 같은 문장을 덧붙인다(되먹임 시 재고지).

## F-6 (P1) 스모크가 재시도·다중 슬롯 경로를 밟지 않는다
9번은 슬롯 1개 · attempts=1 성공만 검증한다. C-1(재시도)·E-1(슬롯 2개)은
현재 계측기의 사각지대다. 고쳐도 검증할 수단이 없으면 또 배치 사이클에서 발견된다.

- 스모크 **9b.foundry.retry (billable)** 신설:
  `dryRunSlot(TW_SMOKE_SLOT_TEXT, {forceGenerate:true, forceRetry:true})`
  PASS 조건 = `attempts >= 2 && fragDoc != null && gate.pass === true`.
  400/프로토콜 오류가 나면 C-1 회귀로 판정하고 FAIL 사유에 "tool 메시지 순서" 를 명시.
- 스모크 **9c.foundry.budget (비과금)** 신설:
  `toolkit.resetRequest()` 후 `setPhaseBudget("triage")` → 더미 invoke 를 상한까지 반복,
  이어서 `setPhaseBudget("generate")` → 다시 상한까지 반복.
  PASS 조건 = generate 단계가 phase 상한만큼 실제로 실행됨(= total 이 먼저 고갈되지 않음).
  E-1 회귀를 과금 없이 잡는다. 더미 툴은 `list_schemas`(읽기 전용) 로 한다.
- `TW_SMOKE_SKIP_LLM=true` 일 때 9b 는 SKIP, 9c 는 **실행**한다(비과금).
