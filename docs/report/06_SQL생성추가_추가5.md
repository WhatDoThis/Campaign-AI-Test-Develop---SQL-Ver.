## M-1 (P1) limitSelect 방언 조립 오류 — 구문 오류 + 이중 래핑 잔재

### 문제 1: DISTINCT / TOP 순서 (MSSQL)
T-SQL 문법은 `SELECT DISTINCT TOP n ...` 이다. `SELECT TOP n DISTINCT ...` 는 구문 오류.
현재 `limitSelect` 는 `head = "SELECT TOP n "` 뒤에 `selectList` 를 그대로 이어 붙이는데,
`_toolProbeValues` 가 `selectList` 에 `"DISTINCT col AS tw_val"` 를 섞어 전달한다.

### 문제 2: limit() 잔존으로 인한 이중 래핑 (전 방언 공통)
`limit(sql, n)` 이 `limitSelect("*", "(" + sql + ") tw_lim", "", n)` 을 호출한다.
- 인자 `sql` 이 이미 `ORDER BY` 를 포함하면 MSSQL 에서 파생 테이블 ORDER BY 오류.
- PostgreSQL 에서도 래핑 지점이 둘로 갈려 중첩 깊이 추적이 불가능하다(실제로 `_toolProbeValues`
  에서 한 겹 더 쌓이고 있었음). **방언과 무관한 코드 위생 문제이므로 반드시 수정한다.**

### 수정 A — `dialect().limitSelect` 시그니처 변경
```js
// limitSelect(selectList, fromClause, whereSql, n, opts)
//   opts = { distinct: false, orderBy: "1" }
// selectList 에 DISTINCT 를 직접 넣지 말 것 (방언별 위치가 다름).
function limitSelect(selectList, fromClause, whereSql, n, opts) {
  var lim = Number(n) || DEFAULT_SAMPLE;
  var o = opts || {};
  var dis = o.distinct ? "DISTINCT " : "";
  var ob = (o.orderBy === null) ? "" : String(o.orderBy || "1");

  // T-SQL: SELECT [DISTINCT] [TOP n] select_list
  var head = isMssql
    ? ("SELECT " + dis + "TOP " + lim + " ")
    : ("SELECT " + dis);

  var s = head + selectList + " FROM " + fromClause;
  if (whereSql) s = s + " WHERE " + whereSql;
  if (ob) s = s + " ORDER BY " + ob;
  if (isOracle) s = s + " FETCH FIRST " + lim + " ROWS ONLY";
  else if (!isMssql) s = s + " LIMIT " + lim;
  return s;
}
```
- `orderBy: null` 을 명시하면 ORDER BY 를 생략한다(파생 테이블/집합연산 래핑 시 사용).
- Oracle 은 `DISTINCT` + `ORDER BY 1`(select 리스트 서수 참조)이 유효하므로 그대로 둔다.

### 수정 B — `limit(sql, n)` 제거
- `dialect()` 반환에서 `limit` 를 **삭제**한다. 래핑 지점을 `limitSelect` 하나로 통일.
- 레포 전체 `.limit(` grep → 호출부를 전부 `limitSelect` 로 전환.
- 완성된 SELECT 에 상한만 씌워야 하는 지점은
  `limitSelect("*", "(" + sql + ") tw_lim", "", n, {orderBy: null})` 로 대체한다.

### 수정 C — 호출부 정리
- `testWooProbe.js` `run()` 샘플: 현행 유지, 새 시그니처 호환만 확인
  `dial.limitSelect(kc + " AS tw_key", "(" + inner + ") tw_sample", "", lim)`
- `testWooToolkit.js` `_toolProbeValues`: `selectList` 에서 `DISTINCT` 문자열 **제거**
  `dial.limitSelect(col + " AS tw_val", table, col + " IS NOT NULL", limit, {distinct:true})`
- `testWooDedup.js` EXCEPT/MINUS 대칭차 쿼리에서 래핑을 쓰는 지점은 `{orderBy: null}`
  (집합 연산 내부 ORDER BY 금지)

### 수정 D — 검증되지 않은 DBMS 런타임 가드 (신규)
`testWooProbe.js` `preflight()` 끝부분에 추가. 분기 존재가 곧 지원 보장으로 오해되는 것을 막는다.
```js
var dbt = String(application.getDBMSType() || "").toLowerCase();
if (dbt.indexOf("postgres") < 0) {
  logWarning("[testWoo.probe] 검증되지 않은 DBMS: " + dbt +
    " — dialect() 분기는 PostgreSQL 에서만 실동 검증됨. " +
    "probe/dedup 생성 SQL 을 직접 확인할 것");
}
```
- `preflight()` 반환에 `{dbms: dbt, dialectVerified: (dbt.indexOf("postgres") >= 0)}` 를 포함한다.
- 경고일 뿐 **차단하지 않는다**(정상 진행).

### 수정 E — FDA 확장 여지 주석 (신규)
`getDBMSType(name)` 은 데이터소스명을 받으며 미지정 시 `nms:default` 를 사용한다.
FDA 로 외부 데이터소스를 붙이면 fragment SQL 대상 방언이 달라질 수 있다.
`dialect()` 함수 상단에 주석으로 남길 것:
```js
// 현재는 nms:default 기준. FDA 외부 데이터소스 지원 시
// dialect(dsName) → application.getDBMSType(dsName) 으로 확장 필요.
```
- 지금 구현하지 말 것. 주석만.

### 검증
- 현재 DBMS(PostgreSQL)에서 `probe_values` / `probe_sql` / dedup L3 회귀 확인.
- `dialect()` 의 `isOracle`/`isMssql` 을 강제 주입해 **생성 SQL 문자열만** 출력·대조
  (실행하지 않는다. 문자열 정합성 확인 목적):
  - MSSQL:  `SELECT DISTINCT TOP 50 col AS tw_val FROM tbl WHERE col IS NOT NULL ORDER BY 1`
  - Oracle: `SELECT DISTINCT col AS tw_val FROM tbl WHERE col IS NOT NULL ORDER BY 1 FETCH FIRST 50 ROWS ONLY`
  - PG:     `SELECT DISTINCT col AS tw_val FROM tbl WHERE col IS NOT NULL ORDER BY 1 LIMIT 50`
- 위 대조는 `tools/` 하위 순수 문자열 단위 점검 스크립트로 두어도 좋다(DB 접속 불필요).

## M-2 (P2) 스모크 6번 검출력 불확실 — getIfExists 경로 미보장

### 문제
`twStepQueueRoundTrip` 이 `testWoo.repo.getQueueStatus(qid)` 에 의존하는데,
이 함수가 내부적으로 `operation="select"` 를 쓴다면 N-1(getIfExists 파싱) 회귀를 **잡지 못한다**.
스모크의 존재 이유가 그 회귀 검출이므로 경로가 보장되어야 한다.

### 수정
1. `new_ver/js/testWooRepository.js` 의 `getQueueStatus` 가 어떤 operation 을 쓰는지 확인.
2. `getIfExists` 경로가 아니면 스모크가 **실제 getIfExists 경로를 직접 타도록** 보강한다.
   - `testWoo.foundry._getQueue` 를 `peekQueue(id)` 로 public 화(읽기 전용·부작용 없음), 또는
   - 스모크 내부에서 동일한 `operation="getIfExists"` queryDef 를 직접 구성해
     `res.@id` 판정과 필드 파싱을 검증.
3. 스모크 6번은 다음 3가지를 모두 확인해야 한다:
   - getIfExists 결과에서 `@id` 가 읽히는가
   - 존재하지 않는 id(예: `-1`) 조회 시 **null 반환**, 예외 아님
   - 필드값(`status="queued"`)이 기록값과 일치하는가
4. 스텝을 `6a.queue.write-read` / `6b.queue.miss` 로 분리해 각각 리포트.

### 주의
- 무매치 검증(`-1`)은 부작용이 없으므로 더미 생성 전에 수행해도 된다.
- 더미 레코드 `finally` 삭제 로직은 현행 유지(실패 시 `logError` 로 수동 삭제 안내).

## M-3 (P2) 스모크 1번 — testWoo 전역 부재 시 로그 노이즈

### 문제
`testWoo` 자체가 undefined 이면 14개 모듈이 전부 missing 으로 나열되어
"loadLibrary 실패" 라는 진짜 원인이 묻힌다. 스모크는 장애 상황에서 읽는 산출물이다.

### 수정
```js
function twStepGlobals() {
  if (typeof testWoo === "undefined" || !testWoo) {
    twFail("1.globals", "testWoo 전역 자체가 없음 — loadLibrary 실패. " +
      "JS 라이브러리 배포 여부와 woo: 네임스페이스를 먼저 확인할 것");
    return false;
  }
  var names = [...];
  // 이하 기존 루프 유지
}
```
- 개별 모듈 누락과 전역 부재를 **다른 메시지**로 구분한다.

### 부수 (선택)
스모크 요약에 `preflight()` 가 돌려준 `dbms` / `dialectVerified` 를 함께 출력해
어떤 DB에서 검증된 결과인지 로그에 남긴다.

## 검증 절차
1. `tools/checkRhinoSyntax.js` 전체 통과.
2. 스모크 전 스텝 PASS (6a/6b 분리 반영).
3. 존재하지 않는 큐 id 조회 → 예외 없이 null (M-2).
4. `probe_values` / `probe_sql` / dedup L3 정상 동작 (M-1 회귀).
5. 방언 3종 생성 SQL 문자열 대조 통과 (M-1, 실행 없음).
6. 레포 전체 `.limit(` grep 결과 0건 (M-1 수정 B 완료 확인).
7. PostgreSQL 환경에서 `dialectVerified: true` 확인, 경고 미발생 (M-1 수정 D).
8. `foundry.enabled=false` 회귀 경로 정상.

## 로그
`docs/log/log.md` 에 신규 항목 추가. M-1/M-2/M-3 원인·수정·근거 URL 기록.

## 금지
- `selectList` 문자열에 `DISTINCT` 직접 삽입.
- 파생 테이블/서브쿼리/집합연산 내부에 `ORDER BY` 생성.
- `getIfExists` 결과에 `.length` / `[0]` / 컬렉션 접근.
- 예외를 빈 catch 로 삼키기.
- woo:* 커스텀 스키마 물리 컬럼명 추정 SQL.
- Oracle/MSSQL **실행** 검증을 전제로 한 코드·문서 작성(문자열 정합까지만).
- 기존 P0~P2, N-1~N-6, S-1 수정 되돌리기.
