# 조건·테이블·컬럼 — 쉬운 설명

> **누구용:** 기획·운영·개발 공통  
> **한 줄:** AI Studio는 **컬럼 이름**으로 테이블을 고르지 않고, **미리 등록한 조건 조각(fragment)** 으로만 SQL을 만든다.

---

## 1. 먼저 이것만 기억

| ❌ 이렇게 동작하지 **않음** | ✅ 실제 동작 |
|---|---|
| "sRegion이니까 알아서 테이블 찾기" | fragment마다 **어느 테이블·어느 컬럼**인지 이미 정해져 있음 |
| "값 목록이 같으면 같은 컬럼" | **의미(축)** 가 다르면 **다른 fragment** |
| "AI가 SQL에 컬럼명을 새로 씀" | AI는 **조각 고르기만** · SQL 조립은 **규칙 엔진** |

비유: **레고 블록**  
- 블록(fragment) = "고객 테이블 · 거주지 · 전남"  
- 블록(fragment) = "요금 테이블 · 요금제 · 학생요금"  
- 마케터 말 = "전남 + 학생요금" → 블록 2개 골라 **AND(교집합)** 로 조립

---

## 2. fragment 안에 뭐가 들어 있나

하나의 fragment = **한 조건** (예: "거주지가 전남")

| 항목 | 쉬운 말 | 예 |
|---|---|---|
| `sql_text` | **어느 테이블**에서 **어느 컬럼**을 보는 SQL | `FROM Customer WHERE sRegion IN ({{region}})` |
| `_source` | 그 조건의 **주소** (스키마·컬럼·의미) | Customer 테이블 · sRegion · "거주지역" |
| `concept` | **무슨 종류** 조건인지 (축) | `residential_region` (거주) vs `billing_region` (청구지) |
| `nlMap` | **한글 말 → DB에 저장된 값** | `"전남" → "전남"` 또는 `"전남" → "46"` |
| `tags` | 검색용 **꼬리표** | region, plan … |

**중요:** 컬럼 이름(`sRegion`)만 같다고 **같은 조건이 아님**.  
**테이블 + 의미(concept) + nlMap** 이 세트로 묶인다.

---

## 3. 사용자가 문장 입력하면 (전체 흐름)

```
[입력] "전남에 살고 학생요금 쓰는 고객"
    ↓
① 말 쪼개기 — "전남" / "학생요금" (EnPivot)
    ↓
② 라이브러리에서 맞는 블록 찾기 (Stage A)
    ↓
③ 각 블록의 값 사전(nlMap)에 있는지 확인 (M1~M3)
    ↓
④ 블록 조합 계획 (Pass1) → AND 로 묶기
    ↓
⑤ SQL 조립 (Compiler) → 검증 (Gates)
```

맞는 블록이 **없으면** → 지어내지 않고 **"아직 등록 안 됨"** 으로 멈춘다.

---

## 4. 케이스 A — 테이블은 다른데 **컬럼 이름이 같을 때**

### 상황 예

| 테이블 | 컬럼 이름 | DB에 실제 저장 |
|---|---|---|
| 고객 | `sRegion` | `전남`, `서울` (한글) |
| 청구 | `sRegion` | `46`, `11` (코드) |

이름은 둘 다 `sRegion` 이지만 **테이블·값 형식·의미**가 다르다.

### 시스템이 하는 일

1. **fragment를 2개** 등록한다 (각각 다른 `sql_text`, `_source`, `nlMap`).
2. 사용자가 "전남에 **사는**" → **거주지** fragment만 후보.
3. "청구지가 전남" → **청구지** fragment (별도 등록 필요).
4. 각 fragment는 **자기 nlMap만** 본다.  
   - 고객 쪽: `"전남" → "전남"`  
   - 청구 쪽: `"전남" → "46"`

### 결과 표

| 사용자 의도 | fragment | 결과 |
|---|---|---|
| 거주지 전남 | 고객·거주 fragment | ✅ SQL 생성 |
| 청구지 전남 (등록됨) | 청구·청구지 fragment | ✅ SQL 생성 |
| 청구지 전남 (미등록) | 없음 | ❌ unmatched |
| 한 fragment 안에 "전남"이 두 군데 매칭 | — | ⚠️ ambiguous → 확인 칩 |

**운영 팁:** 컬럼명이 같아도 **concept(의미)** 와 **nlMap(DB값)** 을 테이블마다 따로 등록한다.

---

## 5. 케이스 B — 테이블·컬럼은 다른데 **값 종류가 비슷할 때**

### 상황 예

| 테이블 | 컬럼 | 값 예 |
|---|---|---|
| 고객 | `sRegion` | 서울, 전남, … |
| 가입 | `sPlanLabel` | 학생요금, LTE, … |

어떤 컬럼은 Y/N만 쓰고, 다른 컬럼도 Y/N만 쓰는 식으로 **값 집합만** 겹칠 수 있다.

### 시스템이 하는 일

1. **값 목록이 같다고 컬럼을 연결하지 않는다.**
2. "학생요금" → **요금제 축** fragment의 nlMap에서만 매칭.
3. "전남" → **지역 축** fragment의 nlMap에서만 매칭.
4. Pass1이 블록 2개를 AND로 묶고, grain(보통 `sCustomer_id`) 기준 **교집합 SQL** 생성.

### 함정

| 상황 | 결과 |
|---|---|
| 요금 fragment에만 "학생요금" 등록 | ✅ 정상 |
| 실수로 지역 fragment nlMap에도 "학생요금" | ⚠️ 축이 겹치면 ambiguous |
| 값은 맞는데 그 컬럼 DISTINCT에 없음 | ❌ value_not_in_domain → Foundry/heal |
| fragment 자체가 없음 | Foundry가 **컬럼 후보 탐색 → 값 확인 → 새 fragment** |

**운영 팁:** "값이 같다"가 아니라 **"이 말은 어떤 축(의미)인가"** 로 fragment를 나눈다.

## 6. 한 장 요약

```
┌─────────────────────────────────────────────────────────┐
│  NL "전남 + 학생요금"                                    │
│       │                    │                            │
│       ▼                    ▼                            │
│  [거주지 fragment]    [요금제 fragment]                  │
│   Customer.sRegion     Subscription.sPlanLabel          │
│   nlMap: 전남→전남     nlMap: 학생요금→학생요금         │
│       │                    │                            │
│       └──────── INTERSECT ─┘  (같은 고객 ID)            │
└─────────────────────────────────────────────────────────┘
```

| 질문 | 답 |
|---|---|
| 컬럼명 같으면? | 테이블·concept·nlMap 으로 **별도 fragment** |
| 값 종류 같으면? | **자동 연결 안 함** · 축(concept)으로 구분 |
| JS에 if (컬럼명) 추가? | **금지** · 카탈로그/Foundry로 흡수 |
| AI가 SQL 직접 작성? | **금지** · fragment 조립만 |

## 7. Studio 「이전 질문」 저장 — Option vs 스키마

### 증상

질문을 여러 번 보내도 **목록이 1개만 갱신**되는 것처럼 보임.

### 원인 (기술)

| 저장소 | 한계 |
|---|---|
| ACC **Option** (`testWooAiNlRecent_{login}`) | 문자열 **약 1KB** · 한글 10문장 넣기 어려움 |
| 서버 push 응답 | 용량 trim 후 **짧은 목록** → 예전 코드는 UI를 덮어씀 |

### 현재 정책 (v=202~)

| 역할 | 저장 |
|---|---|
| **정본 (UI)** | 브라우저 **sessionStorage** `twStudioRecentNl` · 최대 10개 |
| **보조** | Option · 재접속 시 **병합**만 (로컬 목록을 줄이지 않음) |
| UI 문구 | 「이전 질문 (이 창 기준 최대 10개)」 |

같은 브라우저 탭/창에서는 **질문이 쌓인다**.  
새로고침·다른 PC·다른 브라우저까지 10개 유지가 필요하면 **스키마**가 맞다.

### 선택지 비교

| 방식 | 장점 | 단점 | 추천 |
|---|---|---|---|
| **A. sessionStorage만** (현재) | 배포 쉬움 · 10개 OK | 창/PC마다 다름 | ✅ **지금 PoC** |
| **B. Option만** | 서버 1곳 | 1KB · 10개 불가 | ❌ |
| **C. 1개만 표시** | 단순 · Option 가능 | UX 제한 | △ 차선 |
| **D. 스키마** (`testWooAiNlRecent`) | 로그인별·10+ · 영구 | schema+form+JSSP 배포 | ✅ **운영 전환 시** |

### 스키마 도입 시 (참고 설계)

| 필드 | 용도 |
|---|---|
| `operator_id` / login | 누구 질문인지 |
| `nl_text` | 질문 (longtext) |
| `asked_at` | 시간 |
| 정리 | 로그인당 최근 N건 DELETE 후 INSERT 또는 upsert |

**판단:**  
- **지금 단계:** sessionStorage 정본으로 **수정 완료** (Option 의존 제거).  
- **운영·다기기:** 스키마 추가를 **phase 2** 로 권장. Option으로 10개를 맞추려는 시도는 중단.
